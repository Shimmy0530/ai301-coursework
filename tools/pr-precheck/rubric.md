# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `diff-within-plan` | Every file and every hunk in the diff, read against the plan's Files list, its in-scope and not-in-scope lines, and any deviation note in the plan | Every changed file is named by the plan (naming its folder counts, and "a changelog entry" names the changelog file), and every hunk does work the plan's scope describes: the fix, a test of the fix, or an entry file the plan or the repo's template asks for. Fails on any hunk that adds a flag, option, setting, or feature the plan did not ask for, renames or rewrites code the fix does not need, or edits a file the plan never names, unless a deviation note in the plan records that change. A test that exercises the planned change counts as in scope even if the plan did not list it. | required |
| `plan-delivered` | Each deliverable the plan's scope and approach name (a code change, a test, a docs or changelog entry), read against the diff; the plan's deviation or deferral notes; the description | Every deliverable the plan names is present in the diff, or its absence is recorded in the plan (a deviation or deferral note) AND stated in the description. Fails when a named deliverable is missing with no note, or when the note exists in only one of the two places. An omission disclosed in both places is an honest shortfall and passes. | required |
| `description-matches-diff` | Every sentence in the description that says what the diff does, does not do, or adds (files touched, tests added, entries added, "no changes beyond the plan", "no X added"), read against the diff | Each such claim is true of the diff. "Implements the plan exactly" or "no changes beyond the plan" is false if `diff-within-plan` found an unplanned hunk; "docs added", "changelog added", or "tests for X added" is false if no such hunk exists; "no options added" is true when no hunk adds one. Imprecise wording a reviewer would not be misled by (a helper function added beside the named function) does not fail; a claim that hides an extra file, a new feature, or a missing deliverable does. | required |
| `repro-rerun-shown` | The PR's test evidence, read against the plan's test plan and the repro input it names | The evidence re-runs the input or command that showed the bug (the plan's repro step, or a test that encodes that input) and names the observable result before and after, where the after is the plan's expected-after and differs from the before. Every failure mode the plan's test plan names as a repro to re-run is shown; a control may be stated as unchanged. Fails when the evidence is a summary with no input named ("tested locally", "works on my machine", "verified for a day"), or when the only input shown is a control or a path the change does not touch. | required |
| `repo-checks-run` | The test-evidence section and the description's testing section, read against the checks the repo-facts block or the plan's test plan names (the suite, lint, type, or format commands) | The repo's own suite or check command is named with its outcome: a pass with the command stated, or a failure reported with its reason. "All tests pass" or "CI will tell" with no command named fails. A check honestly reported as failing for a stated reason outside the change passes this check. | required |
| `no-debris` | Every hunk in the diff, and the commit list | The diff contains no debug output statements (print, eprintln, console.log, dbg and the like), no commented-out code, no unused or dead functions, variables, or imports, no TODO, FIXME, WIP, or XXX markers, and no hunk whose only effect is whitespace, re-indentation, import re-ordering, or re-printing unchanged lines. Explanatory comments, docstrings, and unchanged lines that re-appear inside a hunk that also changes a functional line are not debris. | required |
| `template-asks-met` | The repo-facts block's `pull requests` line (template sections, checklist, issue-reference line, changelog or whatsnew entry, tests), read against the description and the diff; live, the repo's PR template and contributing document | Every ask the repo states is honored: each named template section or checklist is present in the description with content specific to this change (not blank, not boilerplate), a required issue-reference line (closes or fixes #N) is present, a required changelog or whatsnew entry is in the diff, and tests asked for behavior changes are in the diff. Passes when the repo states no template and no asks. | required |
| `ai-disclosure` | The repo-facts block's contribution policy line (live, the repo's contributing document and the scope's house rules), read against the description | If the stated policy requires AI-use disclosure, the description discloses AI use in the author's own words (the tool used or the extent of the assistance). Treat every package as AI-assisted work. Passes when no stated policy requires disclosure. | required |
| `thread-direction-honored` | Thread entries by OWNER, MEMBER, or COLLABORATOR that state a direction or ask a question about the change, read against the description and the diff | The PR follows any direction a maintainer stated and answers any question a maintainer asked about the change's design. Passes when no maintainer stated a direction. | preferred |

## Verdict rule

Accept only if every required check is `pass`. Any required `fail` or
`unclear` means reject: an `unclear` grade is a claim the package cannot
verify, and an unverifiable PR is not ready to submit. Preferred checks
are reported but never change the verdict. Honest disclosure is not a
shortfall: a PR that delivers less than the whole plan, with the gap
recorded in the plan and stated in the description, can accept.
